轨迹回放 × 游戏复刻质量评估 Skill 总结

本页是对 skill/player/ 目录下「真实鼠标注入 + 键鼠序列回放」Skill 的总结， 整理自 4 份文档、2 份 C# 实现、2 份示例数据与 2 个一键脚本。 核心用途：产出一份可在不同游戏构建之间交叉复现的键鼠轨迹（trajectory），回放到复刻游戏上， 通过逐层对比结果来量化"游戏复刻得好不好"。

一句话评估逻辑：把同一份 sequence.json 轨迹喂给复刻游戏—— 如果复刻得足够好，轨迹应该能完整走完 91 个事件，并得到与录制端完全一致的终局与逐回合状态； 任何偏差（点击落空 / 菜单错位 / 逻辑分歧）都会让回放中断或结果偏离，即直接暴露复刻缺陷的位置。
✓ 实战验证：OpenAW3D 91 事件完整对局（2026-09） OS 级真实输入 · 人机等价 不改游戏源码即可回放 跨构建 / 跨机器可复现

1一图看懂：轨迹评估闭环

整套 Skill 就是一条「录制 → 回放 → 对比」的流水线。轨迹在录制端（带内挂的游戏）生成， 在回放端（复刻的游戏、不改源码）重放，两端的产物逐层对比即得到复刻质量结论。

① 录制端

带内挂的游戏自动跑完一局

  • AGInputInjector.cs（通用注入器）
  • AGGameAdapter（按游戏适配）
  • 所有操作经 xdotool OS 级鼠标事件注入，与人类操作等价
  • 固定相机 + 固定 RNG 种子
→
② 轨迹产物

三件套 trajectory

  • sequence.json — 91 个键鼠事件（坐标+时序）
  • recording.mp4 — 完整对局录像
  • battlelog.json — 逐回合状态快照（真值）
→
③ 回放端

复刻游戏上重放轨迹

  • SequenceReplayer.cs 放入 Assets（不改游戏代码）
  • 相机固定到录制时参数
  • 场景就绪屏障 + 客户区坐标自纠错
→
④ 评估 (EVA)

逐层对比 → 复刻质量

  • done.json — 执行完整度
  • battlelog diff — 逻辑一致性
  • replay.mp4 — 视觉一致性（VLM）
为什么轨迹能跨游戏版本？序列只记录屏幕坐标 + 按键 + 时序， 不含任何 InstanceID / 内存地址 / 对象引用。所以同一份轨迹可以拿到任何一份构建（原版或复刻版）上重放， 是天然的"复刻一致性测试用例"。

2核心原理：真实输入驱动（人机等价）

源自 RealInputPrinciple.md / RealInputMigration.md。这是轨迹可作为评估依据的合法性根基。

✕严格禁止（内挂直调）
SendMessage("OnMouseDown")
反射调用 OnButtonPress(item)
直接调用游戏 manager 方法
hook / 覆盖 Input.GetMouseButtonDown

这些方式绕过输入管线，能点到人类点不到的位置 → 轨迹不可复现，评估无效。

✓必须采用（OS 级真实事件）
  • 点击 = 鼠标移动到屏幕坐标 → 按下 → 抬起
  • Unity 自动物理射线 → OnMouseDown
  • IMGUI / uGUI 事件系统自然响应 Event.current
  • xdotool（X11）注入，与人类按住鼠标完全等价

等价性标准：人类照着录屏轨迹手动操作，必须得到与 bot 完全相同的结果。

关键技术决策 —— 为什么是 xdotool？

候选方案结论
InputSystem StateEvent不生成 IMGUI 的 Event.current，GUI.Button 不响应 ✕
WarpCursorPosition只移动光标，不生成点击事件 ✕
activeInputHandler=Both 桥接只桥接旧 API，不桥接 IMGUI Event ✕
xdotool（XSendEvent，OS 级）引擎自动生成 Event.current，IMGUI / uGUI / 物理射线全部接收 ✓

确定性前提 —— 回放可对比的硬条件

🎲 RNG

固定种子（示例 header 中 seed: 0）

🌐 网络

无网络交互逻辑

⏱ 时间

无 DateTime.Now / realtime 依赖

⚙ 物理

固定时间步长

任一条件不满足，复刻版与录制端会自然偏离——此时偏离不一定是复刻缺陷，需先排除非确定性因素。

3Trajectory 产物与序列格式

一份完整轨迹 = 3 个文件

文件内容评估角色
sequence.json 键鼠操作序列：屏幕坐标 (sx,sy) + 操作类型 + 时间戳 + 前置等待条件 驱动回放的"测试脚本"（示例：91 事件完整对局）
battlelog.json summary（result / winner / days / ops / seed）+ turns[] 逐回合快照（单位 / 建筑 / 资源） 逻辑对比真值（示例：11 回合，red_wins，6 天）
recording.mp4 录制端完整对局录像（所见即所得） 视觉对比真值（人工 / VLM 审查）

序列事件 schema

{
  // header：game / map（主场景名，场景就绪屏障用）/ seed / 分辨率 …
  "header": { "game": "Tanks-Hotseat", "map": "Scene01", "seed": 0 },
  "events": [
    {
      "i": 2,                       // 事件序号
      "frame": 17, "t": 4.03,       // 帧索引 / 时间戳（录制时 unscaledTime 秒）
      "op": "world_click",          // screen_click / world_click / gui_click / right_click / key / scroll …
      "sx": 249, "sy": 367,         // Unity Screen 坐标（左下角原点，Y 向上）
      "meta": "unit@(2,11)",        // 人类可读元数据 → 偏差时可直接定位"本想点什么"
      "inject": "os_mouse",         // 注入方式恒为 OS 级鼠标
      "wait": "game_settled"        // 前置等待条件（场景就绪屏障）
    }
  ]
}
评估利器 meta 字段：每个点击都标注了语义目标（如 "MainMenu/Play"、"tile@(4,7)"、"BuyMenu/Tank"）。 回放失败时，对照 done.json 的中断位置 + meta，一步定位复刻版在哪个 UI / 单位 / 逻辑上出了问题。

4评估指标体系：四层对比判断"复刻好坏"

由浅入深：先看"能不能走完"，再看"结果是否一致"，最后看"画面是否一致"。

层级对比对象指标一致性 ⇒ 结论
① 执行层 done.json（执行事件数 / 总事件数） 91/91 事件全部执行、无崩溃、未超时 轨迹走通 ⇒ 复刻版基础可玩、输入管线正确
② 终局层 battlelog.summary result / winner / days 与录制端一致 终局一致 ⇒ 核心规则（胜负 / 回合）复刻正确
③ 状态层 battlelog.turns[] 逐回合 diff 每回合单位位置 / HP / 建筑归属 / 资源逐项相等 全程一致 ⇒ 移动 / 战斗 / 经济等逻辑逐条复刻正确
④ 视觉层 recording.mp4 vs replay.mp4 帧相似度 / VLM 问答：界面布局、单位位置、动画表现 画面一致 ⇒ 表现层（UI 布局 / 美术 / 镜头）也复刻到位
✓判"复刻好"的证据链
  • 91/91 事件全部执行（done.json）
  • 终局 red_wins / 6 天一致（summary）
  • 11 回合状态 diff = 0（turns）
  • 两段视频逐帧 / VLM 评估一致

⇒ 功能、逻辑、表现三层全对齐，复刻质量高

✕偏差即暴露复刻缺陷
  • 轨迹中断 / 崩溃 → 基础可玩性缺陷
  • 某按钮点不到 → 该 UI 布局 / 交互复刻偏差
  • 过程相似但终局不同 → 数值 / 规则差异
  • 状态一致但画面不同 → 表现层差异

⇒ 配合 meta 字段精确到"哪一步、哪个元素"出错

5完整操作流程

Step 1 · 录制轨迹 （带内挂的游戏构建）

# AGInputInjector.cs + AGGameAdapter 放入游戏工程后构建，运行：
AUTOGAMER_AUTO=true ./game -screen-width 800 -screen-height 600
# → 产出 sequence.json + recording.mp4 + battlelog.json

Step 1.5 · 内挂自检 replay （推荐：先确认 sequence 本身没问题）

# 同一个内挂构建切到 replay 模式，把刚录出的轨迹先重放一遍：
AUTOGAMER_RUN_MODE=replay AUTOGAMER_SEQUENCE=<output>/sequence.json \
./game -screen-width 800 -screen-height 600
# 由内挂侧 AGSequenceReplayer 逐事件调 AGInputInjector.ReplayClick(sx,sy) 按屏幕坐标重放（不解析游戏对象）
自检的意义：同一构建内"录 → 放"一致 ⇒ 排除录制/坐标/时序问题。 之后再在复刻游戏上回放，出现的偏差就更能归因于复刻本身而非轨迹质量问题。 注意：回放循环在 AGSequenceReplayer.cs（内挂侧文件，不在本目录）；AGInputInjector.cs 提供的是 ReplayClick 回放接口 + OnInjected 录制钩子（每条注入 Emit 一个 AGSeqEvent，即 sequence.json 的来源）。

Step 2 · 在复刻游戏上回放 （推荐方案 B：放入 SequenceReplayer.cs 重新构建）

# SequenceReplayer.cs 放入复刻游戏的 Assets/（不改游戏原始代码），构建后：
./game -screen-fullscreen 0 -screen-width 800 -screen-height 600 \
  -sequence /path/to/sequence.json \
  -camera-pos 7.5,20,8.5 -camera-rot 90,0,0 -camera-fov 60 \
  -camera-disable-script StrategyCamera \
  -replay-output-dir /path/to/output \
  -replay-quit-on-end true \
  -replay-record true -replay-record-fps 15
# → 产出 replay.mp4 + done.json + player.log
务必窗口模式启动（-screen-fullscreen 0）：全屏 Player 不接收 X11 事件； 也不要对窗口模式使用 -replay-force-window（overrideredirect 会让窗口管理器重摆窗口，几何不稳，见 踩坑 #3）。

Step 3 · 一键脚本（推荐入口）

脚本作用用法
setup_and_run.sh 检查并安装 xdotool / x11-utils / ffmpeg；把 SequenceReplayer.cs 复制进游戏工程 Assets/Scripts/；给出回放命令 bash setup_and_run.sh <game_project_dir> <sequence.json> [args...]
run_replay.sh 启动游戏 → 查找并持续置顶窗口 → 等待回放完成（300s 超时）→ 打印 done.json 与产物清单 bash run_replay.sh <game_exe> <sequence.json> <output_dir> [args...]

Step 4 · 评估对比

  • 读 done.json：executed / total 事件数、视频路径、帧数 → 执行完整度
  • 对比 battlelog.json：summary 终局 + turns 逐回合 diff → 逻辑一致性
  • 对比两段 mp4：帧 diff / VLM 评估 → 视觉一致性
  • 不一致 → 按 第 8 节诊断表区分"环境问题"还是"复刻缺陷"

7轨迹可复现的技术保障

7.1 坐标链路 —— 从"想点什么"到"OS 点击"的完整传递

以点击红方坦克 unit@(2,11) 为例（示例序列事件 i=2）：

① 碰撞体顶部bounds.center + up×(size.y/2+0.1)，避免被地面/地块遮挡(2.0, 1.13, 10.93)
↓
② WorldToScreenPoint固定相机 (7.5,20,8.5) · Euler(90,0,0) · FOV 60 · 800×600 → Unity Screen 坐标（左下角原点，Y↑）(248.5, 366.9)
↓
③ 转 X11 绝对坐标客户区偏移 (5,56) + 缩放比 + Y 轴翻转（Unity Y↑ → X11 Y↓）(253, 289)
↓
④ xdotool 注入mousemove → mousedown → mouseup，OS 级真实事件，Unity 自动物理射线命中OnMouseDown ✓
链路中任何一环不同（相机位置/角度/FOV/分辨率/客户区偏移），②③④ 步全部点错位置。 回放端相机必须逐参数复刻录制端，这就是 -camera-* 参数存在的意义。

7.2 相机固定参数表 （示例轨迹对应的规格）

参数值说明

7.3 回放端五重自纠错机制

1客户区坐标修正

优先 xwininfo 取客户区绝对坐标；后备 xdotool + _NET_FRAME_EXTENTS 修正外框差值。

2点击前刷新几何

每次点击前重新检测窗口位置/大小，窗口被 WM 移动也能跟上（自纠错）。

3场景就绪屏障

sceneLoaded 后等新场景 + 相机固定完成 + 0.3s 缓冲，再执行下一事件，杜绝"点击落在旧场景"。

4窗口模式优先

-screen-fullscreen 0 启动，避免 overrideredirect 引发的几何抖动。

5窗口持续置顶

run_replay.sh 每 3s windowraise 一次，防止其他窗口遮挡导致点击落空。

＋录像含 IMGUI

WaitForEndOfFrame 读帧缓冲 → ffmpeg（RGBA + vflip），3D 与 OnGUI 界面同时入画，供视觉评估。

8实战踩坑 （OpenAW3D 完整对局回放中验证，均为通用问题）

#1客户区 vs 外框坐标（最致命）
  • 现象：点击整体下移 29px，点 "Play" 实际点到 "Quit"，游戏退出
  • 根因：xdotool getwindowgeometry 返回的是含标题栏的外框坐标；实测 xfwm4 外框 (10,85) vs 客户区 (5,56)（_NET_FRAME_EXTENTS=5,5,29,5）
  • 修复：xwininfo 优先 / FRAME_EXTENTS 修正；对 xfwm4、Mutter、KWin 等所有带装饰的 Linux 桌面都存在
#2场景切换时序过快
  • 现象：事件间隔仅 0.1s，回放时场景需 1-2s 加载，下一点击落在旧场景
  • 根因：Editor 热启动 vs standalone 冷启动加载时长差异巨大，纯时间戳间隔不安全
  • 修复：场景就绪屏障（sceneLoaded + 相机固定 + 0.3s 缓冲）；方案 A 用 wait 字段标注切换点
#3overrideredirect 几何不稳
  • 现象：设置 overrideredirect 后窗口坐标在 (2,55)↔(10,85) 间跳变，点击落点不可预测
  • 根因：WM 失去窗口控制权前后会重新摆放窗口
  • 修复：窗口模式启动优先；overrideredirect 仅作全屏兜底且设置后等 1s；每次点击前重取几何

9回放不一致诊断表 —— 区分"环境问题"与"复刻缺陷"

回放失败 ≠ 复刻一定差。先按此表排除环境因素，剩下的偏差就是复刻缺陷的直接证据。

症状先排查（环境）若排除环境后仍复现 ⇒ 复刻缺陷定位
所有点击整体偏移约一个标题栏高度（29px） 客户区 vs 外框坐标（踩坑 #1）；窗口几何未刷新 通常为环境问题
场景切换后的第一个点击不响应 / 点错 加载时序（踩坑 #2）；方案 A 缺 wait 标注 通常为环境问题；若屏障后仍失败 → 该场景加载逻辑复刻偏差
点击坐标对不上（全部偏移） 相机参数 / 分辨率与录制端不一致 镜头系统 / UI 适配复刻偏差
特定按钮点不到（其余正常） 按钮是否处于动画/禁用状态（人类也点不到的属正常） 该 UI 布局 / 交互逻辑复刻偏差（meta 字段直接指出是哪个按钮）
轨迹走通，但单位不移动 / 行为异常 确定性（RNG / 时间依赖 / 网络） 移动 / 战斗 / 规则逻辑复刻缺陷，用 battlelog 逐回合 diff 定位首个分歧回合
过程一致，终局不同 seed 是否一致 数值公式（伤害 / 资源 / 胜负判定）复刻缺陷
状态层全一致，视频画面不同 录像帧率 / 编码参数差异 表现层（美术 / 动画 / UI 样式）差异，不影响玩法正确性
